# Pol link protocol, version 1

The contract between the **gateway** (Android phone holding the SIM cards, BLE peripheral) and a **client**
(iPhone or Android phone, BLE central). Reference implementations:

- Kotlin: `core/src/main/kotlin/studio/virgule/pol/core/link` (gateway and client), tested in `core/src/test`.
- Swift: `ios/Pol/Link/LinkCore.swift` (client), tested in `ios/PolTests`.
- Test vectors: `vectors.json`, generated by an independent Python implementation (`tools/vectors.py`).

All integers are big-endian. All cryptography is from the platform (JCA / Android Keystore, CryptoKit / Secure
Enclave). Nothing in this protocol is custom cryptography: it composes P-256 ECDH, ECDSA-SHA256, SHA-256,
HKDF-SHA256 and AES-256-GCM in the standard ways described below.

## 1. Bluetooth LE

| Item | UUID | Properties |
|---|---|---|
| Service | `F103B6C9-F328-48B7-9D59-0306C22CE898` | Advertised by UUID; **no device name** in the advertisement. Service data: 1 byte, bit 0 = pairing window open. |
| RX | `844270AB-FE95-4890-9F8B-47EA1D3D77AA` | Write (with response). Client → gateway byte stream. |
| TX | `1E99158F-F772-4FD5-9449-4CFF9EE55C59` | Notify. Gateway → client byte stream. |

The link does not rely on Bluetooth pairing/bonding or link-layer encryption: confidentiality and authentication
come from §3–§4. Chunks are at most `ATT_MTU − 3` bytes; chunk boundaries carry no meaning. The gateway accepts at
most 3 simultaneous connections and drops a peer whose unread output exceeds 512 KiB.

## 2. Records

```
len: u16 | type: u8 | body (len − 1 bytes)        len counts type + body; body ≤ 8192 bytes
```

| type | Name | Direction |
|---|---|---|
| 0x01 | PAIR_COMMIT | C → G |
| 0x02 | PAIR_REVEAL_GATEWAY | G → C |
| 0x03 | PAIR_REVEAL_CLIENT | C → G |
| 0x04 | HELLO (resume) | C → G |
| 0x05 | HELLO_ACK | G → C |
| 0x06 | REJECT `reason: u8` | either |
| 0x10 | SEALED `ctr: u64 ‖ ciphertext ‖ tag(16)` | either |

Any other type, an oversized length, or a malformed field closes the connection. REJECT reasons:
1 bad version, 2 unknown device, 3 pairing closed, 4 busy, 5 declined, 6 authentication failed, 7 too many
attempts, 8 timeout, 9 malformed, 10 revoked, 11 transport.

## 3. Handshakes

Keys are NIST P-256; public keys are 65-byte uncompressed X9.63 points, validated on receipt. Each device has a
long-term **identity** signing key `S` (non-exportable: Android Keystore / Secure Enclave). Every connection uses
fresh **ephemeral** ECDH keys `E` (forward secrecy). `id(S) = SHA-256(S)[0..16)`. `ver = 1`.

### 3.1 Pairing (first contact, numeric comparison with commitment)

Only possible while the gateway's owner has opened the pairing window (3 minutes, closes after one success or
3 failed attempts; every attempt that got past the commitment counts, including a dropped link).

```
C → G  PAIR_COMMIT          ver ‖ c,  c = SHA-256("POL1-commit" ‖ E_C ‖ S_C ‖ n_C ‖ name_C)
G → C  PAIR_REVEAL_GATEWAY  ver ‖ E_G ‖ S_G ‖ n_G(16) ‖ len ‖ name_G
C → G  PAIR_REVEAL_CLIENT   E_C ‖ S_C ‖ n_C(16) ‖ len ‖ name_C          (G checks c)

th   = SHA-256("POL1-pair" ‖ PAIR_COMMIT body ‖ PAIR_REVEAL_GATEWAY body ‖ PAIR_REVEAL_CLIENT body)
SAS  = u32(SHA-256("POL1-sas" ‖ th)[0..4)) mod 10^6, shown as 6 digits on both screens
keys = HKDF-SHA256(ikm = ECDH(e_C, E_G), salt = th, info = "POL1 keys", L = 64)
       k_c2g = keys[0..32), k_g2c = keys[32..64)
```

Because the client commits before it sees the gateway's values, and the gateway reveals before it sees the
client's, an active attacker cannot choose values to make the two codes match; each attempt succeeds by chance
with probability 10^-6. Each person then compares the codes:

- On "codes match", that side sends `SEALED(channel 0xFE, ECDSA_sign(S_self, label ‖ th))`, with label
  `"POL1-sig-client"` or `"POL1-sig-gateway"`. The peer verifies it with the `S` from the reveal.
- Pairing completes only when **both** people confirmed and both signatures verified. The gateway then stores
  `(id, S_C, name_C)`; the client stores `(id, S_G, name_G)`. The session continues as an established session.
- "Codes don't match" sends REJECT 5. Nothing is stored.

### 3.2 Resume (every later connection, mutual signatures, SIGMA-style)

```
C → G  HELLO      ver ‖ E_C ‖ n_C(16) ‖ id(S_C)
G → C  HELLO_ACK  ver ‖ E_G ‖ n_G(16) ‖ len ‖ sig_G         (REJECT 2 if id unknown or revoked)

th    = SHA-256("POL1-resume" ‖ HELLO body ‖ ver ‖ E_G ‖ n_G)
sig_G = ECDSA_sign(S_G, "POL1-sig-gateway" ‖ th)            C verifies with its stored S_G
keys  = HKDF-SHA256(ECDH(e_C, E_G), salt = th, "POL1 keys", 64)
C → G  SEALED(0xFF, ECDSA_sign(S_C, "POL1-sig-client" ‖ th))  G verifies with the stored S_C, re-checks revocation
G → C  SEALED(0xFF, empty)                                  session up
```

**Downgrade:** both sides speak exactly version 1 and refuse anything else (REJECT 1). The version byte is inside
every transcript, so a future multi-version negotiation is covered by the signatures / SAS.
**Timeouts:** 15 s for a handshake, 120 s for the people to compare a pairing code.

## 4. Sealed records

```
nonce = 0x00000000 ‖ ctr(u64)       aad = 0x10 ‖ ctr(u64)       key = k_c2g or k_g2c
plaintext = channel(u8) ‖ payload   channel 0x00 control message, 0x01 call audio, 0xFE pair confirm, 0xFF finish
```

Each direction counts from 0. The receiver requires `ctr` to be exactly the next value: a replayed, dropped,
reordered or tampered record closes the session (reconnecting gives fresh keys). A session never exceeds 2^31
records. Plaintext ≤ 8168 bytes; messages are paged to stay below it.

## 5. Control messages (channel 0x00)

UTF-8 JSON envelope: `{"t": type, "id": n?, "re": n?, "b": {…}}`. Unknown types and fields are ignored (forward
compatibility); a request with an `id` and an unknown type is answered with `error {code: "unsupported"}`.
Times are Unix milliseconds. Client requests that act on the phone carry a client message id `cmid`
(8–40 chars `[A-Za-z0-9-]`); the gateway executes each `cmid` at most once within 24 h, so a retry after a
reconnect never sends a text twice.

| Type | Dir | Body |
|---|---|---|
| `status` | G→C | `GatewayStatus {name, appVersion, battery, charging, sims:[{slot, subId, label, carrier, signal 0–4, network, service, roaming}], defaultVoiceSub, defaultSmsSub, caps:{smsSend, smsRead, smsReceive, callPlace, callControl, callLog, contacts, ussd, simChoice, callAudio, hold, mute, speaker}, sdk}`. Sent after sync and about every 60 s. A client shows a feature only when its `caps` flag is true. |
| `sync` | C→G | `{smsSince, callsSince, contacts, client}` → `status`, `sms.page`*, `calls.page`*, `contacts.page`* (only if shared), `call.state` |
| `sms.page` | G→C | `{items:[Sms], more}`; full sync: newest 1000 messages of the last 90 days |
| `sms.new` | G→C | `{item: Sms}` (includes `cmid` when it is the copy of a client-sent text) |
| `sms.send` | C→G | `{cmid, to, body, subId?}` → `sms.ack {cmid, state: pending\|sent\|delivered\|failed, err?}` (several) |
| `sms.read` | C→G | `{thread}`. Accepted; read state stays on the client (see COMPATIBILITY.md) |
| `calls.page` / `calls.new` | G→C | `{items:[CallEntry], more}` / `{item}` |
| `contacts.page` | G→C | `{items:[Contact], more, first}` |
| `call.dial` | C→G | `{cmid, number, subId?}` → `call.ack {cmid, ok, err?}` |
| `call.state` | G→C | `{calls:[{callId, number, name?, state: dialing\|ringing\|active\|holding\|ended, incoming, activeSince?, subId?}]}` |
| `call.action` | C→G | `{callId, action: answer\|reject\|end\|hold\|unhold}`; hold/unhold need `caps.hold` (gateway is the default phone app); unhold of one call holds the other (swap); failures answered with `error` |
| `ussd.send` | C→G | `{cmid, code, subId?}` → `ussd.result {cmid, ok, text?, err?}` |
| `ping` / `pong` | both | `{ts}` |
| `unpair` | both | `{}`: the receiver deletes the pairing and closes |
| `audio.start` | C→G | `{callId, codecs: ["opus","pcmu"], codec}`: carry this call's audio once it is active; the gateway picks the first codec it supports (`codec` alone = older clients) → `audio.state` |
| `audio.stop` | C→G | `{callId}` |
| `audio.state` | G→C | `{callId, state: starting\|active\|stopped\|failed, codec?, rate?, reason?: not_set_up\|android_version\|not_interceptable\|no_call\|codec\|helper_failed}` |
| `call.dtmf` | C→G | `{callId, digits}` (≤ 20 of `0-9*#`), played by the gateway's phone app; needs `caps.dtmf` |
| `error` | G→C | `{code: unsupported\|permission\|invalid\|no_service\|failed\|busy, msg?}` |

`Sms {id, thread, address, body, ts, dir: in|out, read, subId?, state, cmid?}`,
`CallEntry {id, number, ts, durationS, type: incoming|outgoing|missed|rejected|blocked|other, subId?, name?}`,
`Contact {id, name, phones:[{number, label?}], starred}`.

**Validation (both sides):** numbers `^\+?[0-9*#]{1,32}$` after stripping formatting (Persian/Arabic digits are
normalised); calls and texts refuse `*`/`#`; carrier codes must match `^[*#][0-9*#]{1,30}#$`; texts ≤ 1600 chars,
control characters stripped; strings from the peer are length-bounded before display. The gateway also rate-limits
per minute: 20 texts, 10 calls, 10 carrier codes.

## 6. Call audio (channel 0x01)

Frame: `codec: u8 (1 = Opus, 2 = G.711 µ-law) ‖ seq: u16 ‖ payload`, 20 ms, mono, both directions, at most one
client per call. **Opus** (RFC 6716): wideband 16 kHz voice ("HD"), 32 kbit/s, in-band FEC, max bandwidth
wideband. Packets are rate-independent (the iPhone runs libopus at 48 kHz, the gateway runs Concentus at 16 kHz;
interop checked both ways, see docs/BUILD.md). **G.711 µ-law**: 8 kHz, 160 bytes, the fallback. The gateway's `status.caps.callAudio` is true only when its audio helper is running and the phone
allows call-audio interception (`status.audio` says which step is missing). Frames are sealed like every other record. A
sender that falls behind drops frames **before** sealing, so counters stay contiguous. Receivers buffer 60–200 ms.
Clients write audio with write-without-response (the RX characteristic allows both write types).

On the gateway, a helper process running as the Android shell user (started through Shizuku) uses Android 13's
call-audio interception API (`getCallDownlinkExtractionAudioRecord` / `getCallUplinkInjectionAudioTrack`) and, where
allowed, `MODE_CALL_REDIRECT` to take the phone's own microphone and earpiece out of the call.

## 7. Compatibility rules

- New message types and fields may be added in version 1; receivers ignore what they don't know.
- A change to records, handshakes or sealing requires version 2. Until both sides support it, version 1 is
  refused rather than silently downgraded.
